# RUNBOOK — Eva / Aetherlyn

Действия при инцидентах. Все команды — от пользователя `eva` на сервере
`/opt/eva-bot`, если не сказано иное. Секреты не копировать в чат и тикеты.

## 1. Где что лежит

| Что | Путь |
|---|---|
| Код | `/opt/eva-bot` |
| Конфиг | `/opt/eva-bot/.env` (права 600) |
| SQLite | `/opt/eva-bot/data/eva.sqlite3` |
| Логи | `journalctl -u eva-bot`, `/opt/eva-bot/logs/eva.log` |
| Бэкапы | `/opt/eva-bot/backups/` (14 дней) |
| systemd | `deploy/eva-bot.service` |
| nginx | `deploy/nginx.conf`, `/etc/letsencrypt/live/...` |

## 2. Быстрая диагностика

```bash
systemctl status eva-bot
journalctl -u eva-bot -n 200 --no-pager
curl -sS http://127.0.0.1:8080/health | python3 -m json.tool
grep -E 'ptlc_|sk-|bot[0-9]+:' logs/eva.log | head
```

`/health` отвечает `status: ok|degraded`, `db`, `llm`, `panel`, `rcon`, `kb_chunks`.
Если `db=false` — проблема с файлом/правами/диском. Если `llm=false`, но ключ задан —
проверьте `LLM_BASE_URL`, ключ и сеть; бот продолжит отвечать детерминированно.

## 3. Бот молчит

1. `systemctl status eva-bot` — процесс жив?
2. В логе `InvalidToken`, `Unauthorized` → неверный `BOT_TOKEN`; замените и перезапустите.
3. Webhook: `curl -i https://<домен>/webhook` должен вернуть 401/405, а не 502.
   `502` — бот не слушает `127.0.0.1:8080`; `401` — не совпал `WEBHOOK_SECRET`.
4. Проверьте `getWebhookInfo` у @BotFather / через Bot API: `last_error_message`.
5. Nginx: `nginx -t && systemctl reload nginx`; сертификат: `certbot renew --dry-run`.
6. Если Telegram недоступен из страны хостинга — используйте разрешённый прокси/хостинг;
   polling не является обходом блокировки.
7. После смены токена старый webhook снимается автоматически при старте; при необходимости
   `BOT_MODE=polling` для проверки.

## 4. Ошибки LLM

- В логе `LLMError`/`httpx.TimeoutException` — проверьте провайдера и `LLM_TIMEOUT_SECONDS`.
- Бот не должен падать: при ошибке он отдаёт безопасный отказ и создаёт тикет.
- Если провайдер утёк ключ — немедленно отзовите ключ, выпустите новый, обновите `.env`,
  `systemctl restart eva-bot`. Проверьте логи на `sk-` и удалите утёкшие строки.
- Не включайте LLM, если в базе есть непроверенные посты: модель получит их как данные,
  но всё равно не должна выдумывать. Спорный факт добавляйте только через FAQ-оверрайд.

## 5. Панель и RCON

- `panel: false` в `/health`: проверьте `PANEL_BASE`, `PANEL_KEY`, `SERVER_ID`, 2FA/токен.
- 5xx панели: бот деградирует и пишет «статус недоступен»; не подставляйте выдуманные данные.
- RCON `Auth failed`: `RCON_PASSWORD`/порт; RCON слушает только localhost.
- Консольные команды не работают у владельца: проверьте `OWNER_ID`, TTL 30 с и
  `audit`; каждая команда требует второго подтверждения.
- Аварийная остановка сервера — **только** владелец через панель/консоль, не автоматика.

## 6. База знаний и ингест

- Пустой/устаревший поиск: админ-меню → «Реиндекс». Затем `/health` (`kb_chunks > 0`).
- Ошибка Telethon: проверьте `TG_API_ID/HASH/SESSION`, что аккаунт состоит в каналах.
  Сессия read-only; не запускайте под тем же аккаунтом бота-спамера.
- Новый пост не появился через 10 минут: `journalctl | grep ingest`, проверьте
  `INCREMENTAL_INGEST_MINUTES`, затем `python -m app.kb.ingest_tg --full`.
- Неверный ответ: админ-меню → тикет вопроса → «Ответить». Оверрайд применяется сразу,
  источник помечается как FAQ владельца. Раз в неделю смотрите отчёт по правкам.
- Не добавляйте в посты/FAQ полные номера карт, токены и чужие персональные данные.

## 7. Донат и промокод

- Заявка без подтверждения владельца не выдаёт промокод — это норма.
- «Не выдан»: проверьте ответ консоли в audit, наличие плагина промокодов и шаблон
  `PROMO_COMMAND_TEMPLATE`. Исправьте причину, подтвердите повторно.
- Не подтверждайте оплату по скриншоту автоматически; сверяйте чек вручную.
- При подозрении на мошенничество: отклонить, сохранить заявку, уведомить владельца.
- Полные номера карт не пересылать в тикеты/чат команды.

## 8. Бэкап и восстановление

Планировщик делает копию SQLite ежедневно в 04:20 МСК и хранит 14 дней. Ручной бэкап:

```bash
sqlite3 data/eva.sqlite3 "PRAGMA wal_checkpoint(FULL);"
cp data/eva.sqlite3 backups/eva-$(date +%F-%H%M).sqlite3
```

Восстановление (остановить бота, сохранить текущую БД):

```bash
systemctl stop eva-bot
cp data/eva.sqlite3 backups/before-restore-$(date +%s).sqlite3
cp backups/<нужный>.sqlite3 data/eva.sqlite3
chown eva:eva data/eva.sqlite3
systemctl start eva-bot
curl -sS http://127.0.0.1:8080/health
```

Проверьте: `/start`, вопрос по правилам, тикеты, донат-таблицу. Индекс лежит в той же БД.

## 9. Откат версии

```bash
systemctl stop eva-bot
cd /opt/eva-bot
git status --short
git log --oneline -5
git checkout <предыдущий-коммит>
.venv/bin/pip install -r requirements.txt
systemctl start eva-bot
```

Перед откатом сделайте копию `.env` и БД. Схема SQLite создаётся `create_all`; при
несовместимом изменении моделей восстановите БД из бэкапа.

## 10. Ротация ключей

1. Выпустить новый ключ у провайдера, не отзывая старый.
2. Заменить строку в `.env` (не в чате).
3. `systemctl restart eva-bot`; проверить `/health` и один запрос.
4. Отозвать старый ключ.
5. Проверить `grep -E 'ptlc_|sk-|bot[0-9]+:' logs/eva.log` — совпадений быть не должно.
6. При утечке `TG_SESSION` завершить все сессии аккаунта в Telegram и выпустить новую.

## 11. Безопасность инцидентов

- Подозрение на prompt injection: бот уже блокирует; посмотрите `audit` (`guard_block:*`)
  и `violations` пользователя. Не отвечайте на инструкции из сообщений.
- Попытка доступа к консоли чужим ID: `audit` (`console_denied`), при повторе — blacklist.
- Спам: throttling ставит мут 10 минут; при массовом — добавьте ID в `BLACKLIST_IDS`
  и перезапустите.
- Утечка секрета: отозвать, заменить, проверить логи и историю Git; при попадании в Git —
  очистить историю и считать ключ скомпрометированным.
